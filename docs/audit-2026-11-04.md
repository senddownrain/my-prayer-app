# My Prayer App — code audit and follow-up plan (2026-11-04)

Base examined: `main` at `cb8becf42c9ab2faf3e42ea53a76a501ceafcb7d`.

## Fixes in this pull request

- Add-mode JSON import skips IDs already stored in Firestore instead of overwriting them.
- Both import modes validate backup records; import splits writes into 400-record batches; existing `createdAt` timestamps are restored when possible.
- Destructive sample seeding and old-schema migration require explicit environment confirmation.
- Search and list previews use `item.text` from the current schema, while still supporting old `textVersions`.
- Sharing on browsers without native share uses working notifier functions; new-schema titles are handled.
- The Holy Mass language picker navigates to `/mass/:id?`; scroll indicator uses viewport coordinates.
- Novena logic uses local civil dates, not UTC dates or absolute milliseconds differences.
- The editor stages translation changes and saves reverse links atomically with the prayer.
- Unit tests are run before the existing CI build/deploy workflow.

No Firestore data, rules, or deployed app is modified by this PR alone.

## Important unaddressed risks

### Critical — Firestore permissions and HTML injection

- The repository contains **no version-controlled Firestore rules file**. The live rules have **not** been audited. Authenticated users are not automatically administrators; current UI checks only `authStore.user`. Define an admin allowlist/custom claims and enforce write permissions in Firestore rules, not only in Vue route guards.
- `hidden` is a client-side display preference, not access control: the shared `items` collection is subscribed to by every client. Assume hidden prayers may be readable until server rules and data design prove otherwise.
- `v-html` renders Firestore text in `ItemView.vue`, `HolyMassView.vue`, and `PrayerRuleView.vue` without an allowlist sanitizer. Sanitize on display and import using a maintained library. Preserve permitted Tiptap headings, text colors, alignment, links, and novena `data-day`/`data-marker`; reject scripts, event handlers and dangerous URL schemes. Add browser-focused security tests.

### High — further data and user experience issues

- Imports greater than 400 documents are chunked, so failure after a successful chunk can leave a **partial import**. Show reliable progress/counts, create a restore point before overwrites, and make retries idempotent.
- The data layer subscribes to the entire Firestore collection with `onSnapshot`; add pagination/one-time reads and loading/error states for large catalogs.
- Most personalization (pins, rule, novenas, appearance) is stored in `localStorage`. It does not synchronize between devices or survive all browser-data resets.
- Auth route guard reads `authStore.user` before awaiting initialization; investigate direct navigation to an admin edit route after a full refresh.
- Bidirectional translation groups should be audited for legacy orphaned links and multi-language consistency.
- `useNovenaSuggestions` still needs tests for recurring feasts, invalid dates and already-completed suggestions. Open-tab midnight refresh is not implemented.
- Existing Draft PR #2 for notifications shows notifications immediately when checked and requests permission on startup. This is not a reliable daily schedule, especially when the app is closed: do not merge it without a corrected notification design.
- Existing PR #4 changes the editor's formatting; review and test independently.

## Manual smoke test after merging

1. In admin, **export JSON first**. Prepare a tiny JSON file containing one already-existing ID and one new ID. In **Add** mode, the original prayer must stay unchanged and the new prayer must appear. In **Overwrite** mode, only the explicitly selected existing prayer should change. Do not test with a production backup containing arbitrary changes.
2. Find a prayer by a sentence that occurs in the body but not the title. Confirm both compact search and card preview work.
3. Open a prayer in a browser lacking native Share: pressing Share should copy the public link and show a confirmation.
4. Visit `/mass`, switch language and verify `/mass/<id>` renders the selected text. Refresh the page on that address.
5. Start a novena late in the evening. Date should be local; mark days, reload, and verify progression. Check around month boundaries.
6. Create a language translation of an existing prayer. Save and verify the language switch appears on both prayers. Add a translation but leave the editor without saving: neither prayer should change.
7. Start editing a prayer, type unsaved text, then trigger a Firestore refresh elsewhere. Unsaved text must not be replaced.

Create small PRs with tests and screenshots: (1) enforce admin authorization with a documented Firestore rule set and an emulator test matrix (anonymous reader, authenticated nonadmin, admin); (2) sanitize rendered rich text with an audited library and tests against XSS while preserving prayer formatting; (3) add offline-first error states and true cross-device sync for opted-in personal prayer rules/novena progress; (4) add server-validated backup/restore workflows with a dry-run import preview and progress; (5) polish the mobile prayer reader, accessibility, and internationalization.
